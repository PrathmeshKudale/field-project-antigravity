Part 1. Start here: running this spec in Google
Antigravity
This PDF is a complete build specification for ProofPath: a policy-to-decision platform that turns official vocational and
technical-education documents into reviewed, versioned, executable rules, then answers family questions with claim-level
evidence, quote-verified citations, a deterministic eligibility engine and safe abstention. It is written so that AI coding agents can
implement the whole project from it, with the strongest emphasis on UI, frontend, backend and database.
What you are building (one paragraph)
A React + FastAPI + Postgres/pgvector web app. A parent or student asks a question in English or Hinglish. The backend extracts
atomic claims, retrieves official passages with hybrid search, has an LLM judge each claim, then deterministically validates every
quoted passage against stored page text. A three-valued rule engine computes route eligibility (PASS / FAIL / UNKNOWN) and the
next best question to ask. A pure-code aggregator produces one of five verdicts. Reviewers author and approve rules in Rule Studio
under maker-checker control. An Eval Lab measures the system against baselines.
1.1 Setup in eight steps
1. Create an empty Git repository named proofpath and open it in Antigravity (Editor view).
2. Copy the AGENTS.md from Part 2 into the repository root. Optionally add a GEMINI.md that only says "Follow AGENTS.md;
Antigravity-specific: always produce a plan artifact before editing more than 3 files".
3. Create /docs/spec/ and place this PDF there. Also ask an agent to run "pdftotext -layout" on it into /docs/spec/spec.txt so
agents can grep it.
4. Run Mission M0 (Part 16) first. It scaffolds the monorepo, Docker Compose and CI so every later mission has a stable base.
5. Use Planning mode for missions that touch many files (M1 to M7, M11, M13). Use Fast mode for small fixes and copy edits.
6. Open the Manager view and run independent missions in parallel, following the parallel groups in section 1.3. Review each
agent's plan, then its walkthrough artifact, before merging.
7. After each mission, run make check (lint, types, unit tests, retrieval gate). Do not accept a mission whose acceptance
criteria are not all green.
8. Keep humans in charge of two things: (a) the real policy documents and reviewed rules, (b) the final correctness labels in the
benchmark. Agents must never invent either.

This file is the standing instruction set every agent reads before work. It encodes the invariants that make ProofPath trustworthy.
AGENTS.md
# AGENTS.md  (ProofPath)
## Mission
ProofPath answers family questions about vocational and technical education pathways with claim-level
evidence. LLMs explain; documents prove; a deterministic engine decides; humans review.
## Non-negotiable invariants (a PR that breaks one is rejected)
1. No policy is hard-coded. Eligibility rules live in the `rules` table, authored from source documents,
   approved by a different person than the author (maker != checker), and versioned.
2. The LLM NEVER decides eligibility. The rule engine decides. The LLM only (a) extracts structured fields,
   (b) judges claim-vs-passage stance, (c) explains validated facts.
3. Every citation shown to a user must pass `quote_guard.validate(quote, chunk_text)`: verbatim after
   whitespace/NFKC/casefold normalisation, 6+ words, 25 to 400 chars. Otherwise it is dropped.
4. Missing, stale, superseded or unvalidated evidence => INSUFFICIENT_EVIDENCE or CONTEXT_DEPENDENT.
   Never guess. Abstention is a feature, not an error.
5. Banned output: any guarantee of admission, job, salary, placement or scholarship. Enforced by the
   explain validator AND by tests. "Meets checked conditions" is never "admission confirmed".
6. Retrieved or uploaded text is DATA. Wrap it in <source_data> delimiters. LLM calls have no tools.
   All LLM output must parse into a Pydantic model or the call is retried once, then falls back.
7. No PII in logs, prompts, analytics or LLM cache keys. Run `pii.scrub()` before any external call.
8. While `app_settings.corpus_mode = 'demo'` the UI shows a persistent DEMO DATA banner.
9. Qualification validity, awarding-body recognition, institute approval and placement outcomes are
   separate facts. Never let a positive on one imply the others.
## Stack
Frontend: React 18 + Vite + TypeScript (strict), Tailwind CSS, shadcn/ui primitives (Radix), TanStack Query,
Zustand (UI-only state), React Router, React Flow, Recharts, react-i18next, Vitest, Testing Library,
Playwright, axe-core. Icons: lucide-react. Fonts: self-hosted via @fontsource.
Backend: Python 3.11+, FastAPI, Pydantic v2, SQLAlchemy 2.0 (async) + Alembic, psycopg 3 / asyncpg,
PyMuPDF, httpx, tenacity, structlog, argon2-cffi, PyJWT, slowapi, pytest, hypothesis, ruff, mypy.
Data: PostgreSQL 16 + pgvector + built-in full text search. No Redis, no Celery, no separate vector DB.
Infra: Docker Compose (dev), GitHub Actions (CI), Cloudflare Pages (web), Render free web service (api),
Supabase free Postgres (db). Everything must run with zero paid services.
## Commands (keep these working)
make dev        # docker compose up db + api + web with hot reload
make check      # ruff, mypy, pytest -m "not live", vitest, tsc, retrieval gate
make migrate    # alembic upgrade head
make seed       # load demo corpus, rules, benchmark
make eval-replay# run eval harness against recorded LLM cassettes
make gen-api    # export openapi.json and regenerate TS client
## Conventions
- Python: type hints everywhere, `async def` for I/O, pure functions for rules/aggregation, no globals.
  Modules under backend/app: api, core, db, llm, ingestion, retrieval, pipeline, rules, eval, security.
- TypeScript: no `any`, no default exports for components, feature folders, colocated tests.
- Errors: RFC 9457 problem+json with a stable `code`. Never leak stack traces.
- Every endpoint has a Pydantic request/response model and an integration test.
- Commit style: conventional commits. PRs under ~400 lines of diff where possible.
## Testing rules
- New logic ships with tests. Rule engine and quote guard require property tests (hypothesis).
- LLM calls in tests use cassettes (LLM_MODE=replay). Never call a live model in CI.
- UI: each screen has loading, empty, error, abstain and success stories/tests; axe has zero violations.
## Definition of done
Acceptance criteria in the mission are met; `make check` is green; docs updated; for UI work attach
screenshots (desktop + mobile, light + dark) in the walkthrough artifact.
## Agent workflow
- Plan first when a task touches more than 3 files. State assumptions. Ask only when blocked.
- Open an issue titled "SPEC CONFLICT" if the spec contradicts itself. Do not silently choose.
- Never invent policy text, rule values, citations, statistics or benchmark labels.

3.1 Problem and vision
Families choosing between ITI, Diploma and lateral-entry degree routes face eligibility rules scattered across long regulator PDFs
that change by year and state. General chatbots answer fluently but cannot show where a rule comes from, merge separate
routes, and rarely say "I do not know". ProofPath makes every answer provable, conditional and auditable. It does not push
anyone toward vocational education; it makes pathways easier to understand, verify and navigate.

4.4 Caching and idempotency
•
llm_cache table: key = sha256(provider, model, prompt_version, schema_name, scrubbed_input, corpus_version). Value =
JSON output. TTL 7 days. Invalidated when corpus_version changes.
•
Embedding cache: normalised query text to vector, LRU in memory plus table, to conserve free-tier embedding quota.
•
Idempotency-Key header accepted on POST /reports and admin publish endpoints.
•
corpus_version: integer in app_settings, incremented on any rule publish, source publish or retire. Stored on every qa_event
for reproducibility.

Part 6. UI/UX design system
6.1 Design direction: calm civic editorial
ProofPath handles worries about children's futures, so the interface must feel calm, honest and legible, not like a flashy AI
product. The direction is "civic editorial": warm paper background, deep ink navy, one restrained teal accent, a serif voice for
verdicts and headlines, and generous whitespace. Evidence is treated like a footnote in a good newspaper: always present, never
hidden, beautifully typeset. The result should look trustworthy in a screenshot and feel effortless on a 360px phone.
•
Principle 1, answer first, proof one tap away. Verdict and one-line summary above the fold; every statement links to its
passport.
•
Principle 2, uncertainty is designed, not apologised for. Abstain, context-dependent and stale states have first-class
layouts.
•
Principle 3, ask less. Progressive disclosure; only the next question that matters; no long forms.
•
Principle 4, mobile first, low bandwidth. Self-hosted fonts, no heavy hero images, skeletons instead of spinners, under
200 KB JS on first load for the public routes.
•
Principle 5, never colour alone. Icon + label + colour for every status, WCAG 2.2 AA minimum.

6.7 Microcopy and i18n
•

7.2 Landing and Ask
•
Landing: calm hero in the display serif: "Ask. Verify. Decide." with the sentence "Answers from official documents, with the

Disabled state while submitting.
•
While running: PipelineStepper with four labelled stages fed by SSE. If the server is cold, show "Waking up the server, this
can take about a minute" with a gentle progress animation; never an empty spinner.
•
States: empty, typing, over-limit, rate-limited (shows Retry-After countdown), offline (queues nothing, explains),
server-waking, failure (retry button keeps the text).
•
Data: POST /ask/stream; GET /meta/corpus for the banner and footer freshness.
7.3 Answer screen details
•
VerdictHero: icon, serif headline, one-line summary, "Evidence strength: N of M statements verified" with a segmented
meter (not a percentage). If human review is flagged, show a neutral note: "Queued for expert review".
•
ClaimRows: each atomic claim with status chip (Supported, Not supported, Partly, Need info, Unverified) and "Proof" action
that selects the claim and opens the passport (sticky panel on desktop, bottom sheet on mobile). Keyboard: Up/Down moves
between claims, Enter opens proof.
•
Explanation: 3 to 5 short bullets from the explainer. Each bullet ends with small footnote markers [1], [2] that focus the
matching passport. Language follows the question.
•
NextQuestionChips: appear for CONTEXT_DEPENDENT; tapping a chip asks one tiny inline question and re-runs the rule
engine only (no new LLM call) via POST /pathway/check.
•
Actions: Check my pathway, Save report (prompts sign-in), Report a problem (feedback dialog), Copy link to this answer
(stores only the answer id).
•
AbstainPanel (INSUFFICIENT_EVIDENCE): headline "We could not verify this", short explanation of what is missing, "Who to
ask" (authority name from the intent map, never a made-up URL), and "Try asking this instead" suggestions. It must feel
helpful, not like an error.
•
Stale / superseded: amber FreshnessPill on the affected passport and a note "This source may be out of date; we flagged it
for review".
